# 原理

## 为什么常见的同传工具对不上嘴

它们追求低延迟：听到一句 → 识别 → 翻译 → 马上上屏、马上念。等识别出来，说话人早就说完这句了，
所以字幕和配音总比嘴晚「句长 + 处理时间」（常见 3–10 秒），而且每句晚得不一样，没法靠一个固定偏移补回来。

## 固定延时 D + 源时间戳

- 直播画面和原声整体晚 D 秒播放（默认 30 秒，10–120 可调）。点播提前处理，首段字幕就绪后播放。
- 识别给出每句（到每个词）在源时间轴上的起止 [t0, t1]。播放到 t0 的那一刻上字幕、开始放配音，t1 撤字幕。
- 观众看到的画面比源晚 D，所以只要这句的识别、翻译、合成在「t0 + D」之前做完，就能放回开口的那一刻。
  截止条件：句长 + 等句子结束 + 识别 + 翻译 + 合成 ≤ D。
- 于是：
  - **模型不用流式**：识别、合成都按整句做，用离线质量的模型，只要吞吐跟得上；
  - **翻译可以看后文**：缓冲里往往已经有后面一两句，带着后文翻，半截句、指代不清的问题少很多；
  - **配音可以按时长做**：每句的时长事先知道，翻译时给字数预算，合成时按原句时长控制语速，不串到下一句；
  - **克隆有现成的参考**：每句的原声就在缓冲里，当语气参考；这个人之前最干净的一段当音色参考。
- **画面从不等任何环节**：某句赶不上截止时刻就降级（去掉配音 → 只留原文字幕 → 什么都不加），下一句照常。
  每句各环节的耗时和「离截止还剩多少」（余量）都记下来，观看页和历史页的余量图就是它；D 该调多大看这个数。

## 时间轴

- **节目时间 PT**：拉流切块时，源的时间戳展开成一条只往前走的时间轴（直播断流重连时接着往后排），所有环节都按 PT 记账。
  不用墙钟去对齐字幕和配音。
- **锚点** `anchor.json` = {T0, p0, D}：拉流写好第一块时记下墙钟 T0 和这块的起点 p0。PT 为 p 的画面默认在
  T0 + D + (p − p0) 播出；窗口里的播放器、处理器排配音的截止时刻、可选的 OBS 输出都按这同一个锚点。
- **播放列表**：每场的分段由后端当 HLS 给播放器（`/api/sessions/<场>/media/index.m3u8`），每段带
  `EXT-X-PROGRAM-DATE-TIME`（1970-01-01 加上这段起点的 PT），播放器据此在媒体时间和 PT 之间换算。
  直播只留最近 30 分钟的分段，本地视频全留；只有最近几场保留分段（`keep_media_runs`）。

## 点播与跳转

本地视频和录像链接不按实时速度读取，字幕处理跑在播放前面。解码音频最多提前约 90 秒，控制内存占用。
进度条显示已处理时间范围；跳到未处理位置时，处理器在当前句结束后从目标附近重新识别，重建翻译上下文。
旧字幕保留，已处理区间可以不连续；视频继续播放，字幕在生成后按节目时间出现。
开启 OBS 输出时沿用直播时钟和实时读取，不启用点播提前处理。
处理完成后工作进程等待新的跳转，用户停止场次才退出。
历史回放按源时间轴播放，观看位置保存在当前浏览器或桌面窗口的本地存储中。

## 流水线

```
                         ┌──────────── 本机（Windows / Linux） ───────────┐   ┌─────── Linux（Windows 上是 WSL 2）───────┐
链接 / 本地视频 → ingest：yt-dlp 解析，streamlink 并行下 HLS 分片（画面和声音分开提供时由它合并），ffmpeg 按关键帧切成约 1 秒的 TS（浏览器放不了的编码先转码）
                    │  第一块写好时写锚点
                    ▼
              场次目录 buf/ ──→ processor：每 2 秒把还没提交的音频送识别 ──────────→ 识别服务（CPU）：Parakeet 词级时间戳 + 热词，
                    │            按句末标点断句，声纹在线聚类定说话人 ←─────────    TitaNet 声纹
                    │            碎句同人合并 → 翻译（本地 llama-server，或线上接口）
                    │            → 配音请求（截止时刻最早的先做）─────────────────→ 配音服务（GPU）：IndexTTS-2.5，英语参考克隆中文，
                    │            → events.jsonl：{PT 起止, 中英文, 配音 wav, 音量} ←─  按原句时长单遍控时（vLLM-Omni）
                    ▼
后端 livedub.server（127.0.0.1:8090）：起停服务、开始停止、把 buf/ 当 HLS、配音 wav、记录推给窗口
                    ▼
窗口（Tauri 或浏览器）：hls.js 放分段，按锚点延时 D 播放；字幕按 PT 叠在画面上；WebAudio 按 PT 放配音、压低原声

可选「输出到 OBS」：playout 按同一个锚点取块 → 烧双语字幕 → 按采样位置混配音 → NVENC → 本机 MediaMTX → OBS
```

各进程各自独立，只通过场次目录里的文件打交道（分段、`events.jsonl`、`timing.jsonl`、锚点），哪个挂了能单独重启；
后端重启后按命令行认回还在跑的进程，接着显示。

## 处理器的规则（`livedub/processor.py`）

- **断句**：每 2 秒把从上次提交点到最新的音频（最多 30 秒）送识别。以句末标点（Parakeet 自己会加标点）断句；
  停顿 1.2 秒以上也切（识别偶尔漏掉句号，两个人的话会连成一句）；离窗口末尾不到 1 秒的句子先不提交（后面可能还会长）；
  一整窗都没有标点就在最长的停顿处强制切。
- **说话人**：每句一个 TitaNet 声纹，在线余弦聚类（门槛 0.45，宁拆不合）；不到 1 秒的句子跟上一句同一个人。
- **合并**：太短、没说完的碎句和同一个人的下一句合并（最长 12 秒），换人时绝不合并（配音的声音跟着这一句的说话人）。
- **翻译**：带前 8 句英文做上下文、还没提交的尾巴做后文，术语表命中的词提示给模型，字数上限 = 时长 × 5.5 字/秒；
  超长的再让模型压一次。线上翻译整场用一个只追加的对话（有前缀缓存的接口几乎全命中），上下文到阈值时后台把前文压成摘要。
  重复了上一句已播出的译文的，去掉上文重翻。
- **配音**：每个说话人的音色参考取他第一段 3 秒以上的原声，之后有更长的（最多 12 秒）就换，攒到 6 秒为止；
  这句自己的原声当语气参考。合成按原句时长定倍率（0.85–1.10；译文短时宁可提前说完，也不拖慢），截止前 2 秒还没轮到就跳过。
- **混音**（窗口里的 `app/src/lib/dubAudio.ts` 和 OBS 输出的 `livedub/playout.py` 同一套）：配音归一到同一响度再按原句的
  音量缩放；原声在配音期间压低 15 dB（开口前 0.25 秒渐入，结束后 1 秒恢复，两句间隔不到 1.5 秒就不抬起来）；
  配音提前 50 毫秒让给下一句。

## 实测（参考机：RTX 5060 Ti 16 GB，Windows 11 + WSL 2）

- 开口到配音就绪：中位约 17 秒，p95 约 28 秒（其中约四成是 YouTube 本身的到货延迟），所以直播默认 D = 30 秒。
- 本地翻译（Index-Translate-9B）每句中位 0.5 秒；线上（DeepSeek）每句约 1 秒，缓存命中 96–99%。
- 配音每句约 1 秒；一场 50 分钟的发布会 329 句全部配上。
- 显存：本地翻译约 5 GB，配音约 6.5 GB，窗口 1–3 GB。
- 连续两小时真直播不断流、音画不漂移。

各次实测的过程和数据在 [dev/](dev/)。
