## 显存账：头号风险

| 常驻的东西 | 估算 |
| --- | --- |
| 识别 Parakeet v2 | 2–3G → **实测约 4.0G**（09-30，`docs/实测-M0.md`） |
| 说话人分离 + 声纹 | 约 1G → **Nemotron-3 实测约 0.75G** |
| 翻译 Hy-MT2-7B Q4 | 5.5–6G → **实测约 4.9G**（Windows 原生 llama.cpp） |
| 配音 IndexTTS-2.5 | 约 6G → **bf16 实测 5.3–6.0G**（fp32 要 6.8–7.9G） |
| 人声分离 Kim（只有 B2 需要常驻） | 2–3G |
| **合计** | **15–19G** |
| 可用 | 约 13G（16G 减去桌面程序常驻的约 3G） |

估算下来超了。第一轮实测的头一件事，就是量出每个模型的真实显存。能省的地方，按对质量的影响从小到大排：

1. IndexTTS-2.5 开 BF16。
2. 人声分离不常驻：混音先用 B1（分频压），Kim 只在挑参考音频时按需加载、用完释放。
3. 翻译换 Hy-MT2-1.8B（约 2.5–3G），或者把 7B 的一部分层放到 CPU。
4. 还不够，就让翻译走 API（DeepSeek，每小时一两块钱）。这一条要作者点头。

另外要注意：在 Windows 上显存超了不一定报错，可能溢出到共享内存、变得极慢（03 报告）。所以验收以 `nvidia-smi` 看到的峰值为准。

## 时间账：D = 30 秒够不够

- **最坏的单句（12 秒）**：句长 12 + 端点等待 0.5 + 识别不到 0.5 + 说话人 1 + 等后文最多 4 + 翻译 0.5（实测 p95）+
  TTS 约 11（09-30 实测：12 秒中文 × RTF 0.85 + 约 1 秒固定开销）≈ **29–30 秒，正好顶到 D = 30，没有余量**。
  配音提速到 RTF 0.3 以下之前，要么 D 取 40，要么把句子上限切到 8 秒左右。
- **平均句（4 秒）**：约 10–12 秒，余量很大。
- **整条延时（主播 → 观众）** = 源平台延迟（YouTube 普通模式 10 秒上下）+ D ≈ 40 秒。
- 所以 **D 默认 30 秒，不建议超过 40**。每句的「离截止还剩多少」都要记下来，实测后再定。

## 从调研里定下来的设计

- **时钟**：拉流进程把源 PTS 展开成连续的节目时间 PT（广告、重连造成的跳变都开新段、重新定锚）。
  播出进程在「墙钟 = 锚点 + PT + D」时取数据；缺数据就补帧、补静音，输出时间线永远不跳。
  字幕和配音事件都用 PT 计时，所以天然帧精确、采样精确。
- **字幕**：中英双语（作者 09-30 定）。中文在上、字号大；英文在下、字号小。中文每行不超过 18 字，最多 2 行。
  用 libass 渲染，字体显式指定字体文件（Windows 上 libass 的字体回退不可控）。
- **AI 标注**：画面角落常驻一行「AI 翻译配音」，默认开，可关。
- **翻译**：
  - 用 Hy-MT2 官方的「个性化」模板，带前 2–4 句、后 1 句；后一句用 ASR 中间结果，最多等 4 秒。
  - 只注入本句命中的术语。
  - 字数预算 = 时长 × 4.5 字，超了重试一次。
  - 输出纯文本；「跳过」「合并」这类判断交给外部代码。
  - 术语表分四层（全局 → 厂商 → 本场 → 会话），同一份表导出成 ASR 热词。细节见 02 报告 1.3 节。
- **配音克隆**：
  - 每个说话人一个全局 ID，维护一个参考库：挑 6–12 秒、干净、单人、语气平稳的片段，保留最好的 3 段，稳定后锁定。
  - IndexTTS-2.5 的音色参考用参考库里最好的片段；情绪参考**必须显式传当前这句的原声**（不传就默认拿音色参考当情绪参考）。
  - 新说话人冷启动：先用这句本身（至少 3 秒），或者用同性别的中文预设音色。
- **时长对齐**：
  1. 翻译按字数预算写；
  2. 按自然语速合成，算出倍率 r = 目标时长 ÷ 自然时长；
  3. 0.85–1.15 倍交给 `duration_factor`；
  4. 超出这个范围，一半交给模型、一半交给 rubberband；
  5. r < 0.75 就重译，r > 1.25 就提前收口；
  6. 配音起点放在开口后 0–100 ms（宁晚勿早：声音超前 45 ms 就能察觉）。
- **同传式混音（起步值，听测定）**：
  - 原声人声压 −18 dB；包络在配音开口前 250 ms 开始压，开口时刻压到底；
  - 配音结束 150 ms 后，用 1–1.5 秒升回；句间空隙小于 1.5 秒时保持压低；
  - 节目整体 −16 LUFS，真峰值不超过 −1 dBTP；
  - 不用 ffmpeg 的 loudnorm 单遍模式，也不用 `volume` 做包络。
- **同音色叠两层**：不会是回声，风险是「同一个人同时说两句」的串音感。缓解办法：
  - 压得够深；
  - 配音开口前原声已经压到底；
  - 让原声「退后」：略暗，加一点混响；
  - 参考音频要干。
- **不配音的段落**：
  - 连续唱歌 5 秒以上进入歌曲段，保持原声，字幕可选（加 ♪）；
  - 纯音乐、只有掌声的段落不配音；
  - 音乐段里 ASR 吐出来的字一律当幻觉丢掉。
- **降级**：某句来不及就依次降级：去配音 → 只出字幕 → 不加。迟到率做成指标，用来反推 D。

## 已知风险

1. **显存**：见上面的显存账。
2. **IndexTTS-2.5 在这张卡上的速度**：5060 Ti 的显存带宽只有 4090 的一半不到；有人在 5090 上合成 2.84 秒的短句，RTF 是 1.16，
   说明短句的固定开销大。要用 CUDA Graph 或 vLLM 版的实现，并把相邻短句合并起来合成。
3. **英语参考克隆中文会不会带外国口音**：没有任何公开数据。兜底路线有两条：CosyVoice3 的 `cross_lingual` 模式；
   或者先用中文母语音色合成、再把音色转成主播的。
4. **同音色串音感**：见上面的缓解办法，参数靠盲听定。
5. **拉流**：09-30 在本机和云端环境拉 YouTube，都被「Sign in to confirm you're not a bot」拦下，yt-dlp 换了五种客户端都一样。
   直播拉流可能也会碰上。Twitch 还有广告问题（streamlink 会滤掉，但会留下断点）。
6. **授权**：转播要取得主播或版权方授权；克隆真人声音需要授权，AI 合成内容要标注。所以项目只做给自己看的翻译，
   「输出到 OBS」只是一个由使用者自己负责的开关。
7. **新模型没有社区经验**：Nemotron-3-Diarization 才发布一周；IndexTTS-2.5 在 50 系卡上的坑还没人踩过。

## M0 实测计划

素材：**OpenAI DevDay 2026 Keynote 回放**（https://www.youtube.com/watch?v=Fls_onRviPM ，作者 09-30 指定）。
多人上台、产品名多、有掌声和音乐，正好是发布会场景。下载受阻，见上面风险第 5 条。

1. **环境**：
   - WSL 里按工具各建 venv，互相隔离：NeMo 一个、IndexTTS 一个、llama.cpp 一个；
   - Windows 这边建 uv 项目（streamlink、PyAV、numpy）；
   - WSL 要用的模型放 WSL 自己的盘（隔着 9P 读 Windows 盘上的大模型很慢）。
2. **素材**：
   - 下载 1080p 视频和音轨；
   - 切出三段各 10 分钟：单人主讲、多人演示、带掌声和音乐的段落；
   - 人工标注 100 句的起止，用来量时间戳误差。
3. **逐块基准**（先单独跑，再一起跑）：

   | 块 | 参测 | 看什么 |
   | --- | --- | --- |
   | 识别 | Parakeet v2、Qwen3-ASR-1.7B + 对齐器、Whisper-turbo | WER、句首句尾误差（p90 ≤ 150 ms）、RTF、显存 |
   | 说话人 | Nemotron-3、pyannote community-1 | 句级说话人正确率、ID 是否整场一致 |
   | 翻译 | Hy-MT2-7B Q4/Q6、1.8B；DeepSeek 作参照 | 100 句人工评分、术语命中、字数达标率、延迟 |
   | 配音 | IndexTTS-2.5、CosyVoice3、Qwen3-TTS | 克隆相似度、口音、CER、时长误差、RTF、显存 |
   | 分离与混音 | Kim；B0、B1、B2 × 压 12/15/18 dB | Kim 的 RTF 和显存；盲听串音感和总体偏好 |

4. **全部常驻一起跑 30 分钟**：看显存峰值、总实时率、单句 p99。
5. **M1**：离线出一段带双语字幕和配音的 mp4，给作者看效果。
