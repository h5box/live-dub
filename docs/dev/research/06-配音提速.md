# 配音提速与常驻服务（09-30 实测）

结论先说：

- **单遍控时做成了**：GPT 只跑一遍，按语义码长度算出自然时长和倍率，S2M 和声码器也只跑一遍。
  同一进程、同样 49 句对比，总耗时比两遍法少 **49.7%**；未裁静音的时长误差中位 **0.1%**（两遍法 4.7%）。
- **最快的是 vLLM-Omni 0.30.0**（官方 IndexTTS-2.5 配方，打了本项目的一个小补丁）：
  控时单遍 **RTF 中位 0.22、p90 0.34**，2 秒以下短句单句 **0.59–0.69 秒**，显存约 **6.0G**，达到「≤ 0.3 理想」。
  进程内的几条路（compile、flash-attn 加速、减扩散步数）最好的也只到 0.39–0.50。
- **常驻服务 `dubsvc` 已按 `docs/接口.md` 实现**，默认走 vLLM-Omni，冒烟测试通过。

以下数字都是 DevDay B 段 49 句（`outputs/m0/mt_v2_B.json` 的译文、Nemotron 低延迟档定说话人、`~/live-dub/seg/ref_B/spk*.wav`
作音色参考、这句自己的英文原声作情绪参考），预热之后测，RTF = 墙钟时间 ÷ 未裁静音的输出时长。

## 1. 单遍控时

- 上游的 `duration_factor` 只在 S2M 里用：目标 mel 帧数 = 语义特征帧数 × 1.72 × factor。倍率要在调用前给，所以 M0 只能先自然语速合成一遍、量时长、再整句重跑。
- 做法：`dubsvc/engine.py` 的 `DubEngine` 继承 `IndexTTS2`（不改 `~/live-dub/index-tts`），把 `infer_generator` 拆成
  条件提取 → GPT → 按码长算倍率 → S2M + BigVGAN 四段。倍率 = 目标时长 ÷ 自然时长，限在 0.85–1.25（超出取边界并标 `clamped`）。
  - **坑**：IndexTTS-2.5 的语义编解码器每个 GPT 码解出 **2 帧**语义特征，自然时长要用解码后的长度算
    （码数 × 2 × 1.72 × 256 ÷ 22050 秒）。第一次按码数算，倍率全错成 2 倍、句句顶到 1.25。
  - 顺带：说话人条件按参考路径做字典缓存（上游是单槽，换人就重算 w2v-bert + CAM++）。
- 验收（`bench/tts_single_pass.py --mode compare`，同一进程交替跑，eager、25 步、beams 3）：

| | 两遍法（M0） | 单遍 |
| --- | --- | --- |
| 49 句总耗时 | 291.3 s | **146.5 s（−49.7%）** |
| 时长误差中位，未裁静音（未触界的句子 / 全部） | 4.7% / 6.0% | **0.1% / 0.3%** |
| 时长误差中位，裁掉首尾静音后（未触界 / 全部） | 9.6% / 11.9% | 6.0% / 10.7% |
| 倍率触界 | 20 句 | 20 句 |

- 两遍法误差大，是因为第二遍 GPT 重新采样，生成的码和第一遍不一样长。单遍法没有这个问题。
- **裁静音后普遍偏短约 6%**：输出开头常带 0–0.8 秒近乎无声的段（中位 0.26 秒，跟 M1 量到的开头静音一致），
  裁掉就短了。这段静音不是语义码 52（首尾一个都没有），每句长短不一，按固定值扣也不见效（离线试了扣 0.15–0.3 秒，中位误差仍 5–7%）。
  见「遗留」。
- 触界的 20 句几乎都是 >1.25（中文念得比英文原句短），跟 M0 的结论一致：翻译字数上限该放宽。
- 单遍 eager 的耗时构成（49 句合计 146.5 s）：GPT 77.0 s（53%）、S2M 56.3 s（38%）、声码器 9.4 s、其余 3.7 s。

## 2. 压 RTF

| 路 | RTF 中位 | RTF p90 | 短句（<2 s）单句耗时 | 显存 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 单遍 eager（基线） | 0.63 | 0.89 | 1.30–1.83 s | 载入 5.3G，跑完约 6.1G | |
| a. `use_torch_compile` | 0.59 | 0.80 | 1.17–2.52 s | 载入 5.3G | 只编译 S2M 的 DiT，S2M −12%；变长输入偶尔重编译（那个 2.52 s） |
| b. `use_accel`（flash-attn） | 0.56 | 0.74 | 1.14–1.53 s | 载入 6.9G，torch 峰值 7.1G | GPT −33%（约 110 码/秒） |
| b + a | 0.50 | 0.64 | 1.08–1.29 s | 同上 | |
| b + 扩散 12 步 | 0.39 | 0.50 | 0.71–0.98 s | 同上 | 音质没人听过，只作参考 |
| eager + `num_beams=1` | 0.59 | 0.79 | 1.31–1.75 s | 5.3G | GPT 只快 15%：慢在 HF generate 逐 token 的开销，不在束搜索 |
| **c. vLLM-Omni 0.30.0** | **0.22** | **0.34** | **0.59–0.69 s** | **约 6.0G** | 控时单遍（打补丁）；25 步；GPT 约 317 码/秒 |

- **a. torch.compile**：上游自带开关，只包 S2M 的 DiT（`dynamic=True`）。收益小。
- **b. use_accel**：flash-attn 官方 2.8.3 有现成轮子 `flash_attn-2.8.3+cu12torch2.8cxx11abiTRUE-cp311-cp311-linux_x86_64.whl`
  （torch 2.8 用的是 cxx11abi=True），里面带 sm_120 的核，在这张卡上实测 `flash_attn_with_kvcache` 与 SDPA 结果一致。
  没从源码编译。装在单独的 `~/live-dub/venv-accel`（里面**只有** flash-attn），运行时用 `PYTHONPATH` 叠在 index-tts 的 venv 上。
  - 采样和上游 HF 路径不同：上游只把 temperature 传给加速引擎（默认 top_k 50、top_p 1.0、**没有重复惩罚、没有束搜索**）。
    `DubEngine` 给它补上了 top_k 30 / top_p 0.8，重复惩罚补不了。49 句里没有失控拖长（最长 263 码，秒/字分布与 eager 一致）。
  - 显存多 1.6G（另一份 fp16 的 GPT 加 KV 块）。
- **c. vLLM-Omni**：
  - 社区 index-tts-vllm **没试**：README（2026-03）只支持 IndexTTS 1/1.5/2，不支持 2.5（2.5 的 GPT 多了语言 token 等），
    而且它自己的 TODO 写着 S2M 没加速。
  - 官方配方（recipes.vllm.ai/IndexTeam/IndexTTS-2.5）要 vLLM 0.27+ 加 vLLM-Omni。按 vLLM-Omni 仓库的说明装的是
    **vLLM 0.30.0 + vLLM-Omni 0.30.0**（`uv pip install vllm==0.30.0 --torch-backend=auto`，带来 torch 2.13 cu132），
    新建的 `~/live-dub/venv-omni`，没碰 `~/vllm-qwen3/.venv`。权重直接用 `~/models/IndexTTS-2.5`（它认 `hf_cache/` 布局，不用下载）。
  - 两级进程：stage 0 是 GPT（vLLM，CUDA graph，Triton 注意力），stage 1 是 codec + S2M（DiT bf16 + torch.compile）+ BigVGAN。
    stage 0 的采样和上游一致（重复惩罚 10、top_k 30、top_p 0.8），只是不做束搜索（index-tts-vllm 的 WER 表：beams 3 → 1 差别很小）。
  - **显存**：官方配置两级各占 0.4（16G 卡上要 13G），改成 stage 0 0.26、stage 1 0.15（`dubsvc/omni/indextts2_5_16g.yaml`），
    实测约 6.0G。stage 0 只给 0.2 起不来（GPT 连带 w2v-bert 等条件模型就占 3.57G，KV 没地方放）。
  - **单遍控时要打补丁**：它只认 `speed`（`duration_factor = 1/speed`），调用前就得定。补丁
    `dubsvc/omni/vllm-omni-v0.30.0-target_s.patch`（50 行）让 `extra_params.target_s` 一路传到 stage 1，在那里按码长算倍率
    （同样限 0.85–1.25），并把每句的 `natural_s / factor / clamped` 追加一行到 `/tmp/livedub_omni_factor.jsonl`
    （dubsvc 串行，读最后一行就是这句的，**只有串行时成立**）。启动日志里有 `[live-dub] single-pass target_s patch loaded`。
  - 控时版 49 句：未裁静音误差中位 0.1%（未触界），裁静音后 −6.5%，与进程内版一致；最长 264 码，没有失控。
  - 自然语速（不打补丁、各占 0.33/0.25 时测）：RTF 0.25 / p90 0.37。
  - 冷启动：进程起来约 45 秒，第一句要编译约 18 秒；dubsvc 启动时先合成三句预热，**从启动到 `/health` 200 约 85 秒**（第二次起有编译缓存，60 秒）。

测试环境说明：accel、accel+compile、12 步、beams 1 这几轮跑的时候，主会话的 `svc/asr_service.py`（CPU）和 llama-server
常驻着，GPU 空闲（利用率约 3%），数字和没有它们时的 accel 首轮一致；首轮 accel 有 5 句撞上 llama-server 在跑，已重测。

## 3. 常驻服务 dubsvc

- 代码：`dubsvc/server.py`（HTTP、串行队列、超时 504），后端二选一：
  - `--backend omni`（默认）：转发给 127.0.0.1:8093 的 vLLM-Omni（`dubsvc/omni_client.py`），dubsvc 本身只用 numpy + soundfile；
  - `--backend local`：进程内 `DubEngine`，可加 `--accel --compile --steps N`，作为 Omni 起不来时的后备（RTF 约 0.5）。
- 接口按 `docs/接口.md`：`GET /health`（加载中 503），`POST /synthesize`。返回里多了 `raw_s`（未裁静音的长度，
  倍率控制的就是它）、`queue_s`、`n_codes`。输出 22050 Hz 单声道 16 位，首尾静音已裁（以最响帧 −40 dB 为界，开头留 30 ms、结尾留 30 ms）。
  单句 20 秒没做完回 504（GPU 上的活停不下来，做完丢掉；还在排队的直接跳过）。
- 起停（Windows 这边，都经 WMI 起，SSH 断了也不死）：

```powershell
uv run python -m livedub.server.services start dub --wait   # 先起 vLLM-Omni（:8093），再起 dubsvc（:8092），等到 /health 200
uv run python -m livedub.server.services stop dub          # 两个都停
# 后备：settings.json 里 "dub": {"backend": "local", "args": ["--accel", "--compile"]}
```

- 日志：`.tmp\dubsvc.log`、`.tmp\omni_serve.log`。WSL 侧脚本：`scripts/wsl/dubsvc.sh`、`scripts/wsl/omni_serve.sh`；
  Omni 环境从零重建：`scripts/wsl/setup_omni.sh`（venv + 克隆 v0.30.0 + 打补丁 + editable 安装）。
- 冒烟实测：`/health` 200，`vram_mib` 约 6000；一句 4.2 秒目标的合成 0.97 秒返回；坏请求 400。
- 同时发 3 个请求：依次完成，`queue_s` 0 / 0.9 / 1.8 秒，三句未裁静音都是 4.50 秒（目标 4.5），倍率回传各自对得上。
- `-Stop` 实测：显存降回启动前，`vllm serve` 和两级子进程都没有残留。

## 听审

结果在 `outputs/m0/tts/` 下，每个目录一个 `result.json`：

- `omni/*_omni.wav`：服务现在用的这条路（已裁静音）；
- `sp_compare/*_1p.wav`：进程内 eager 单遍（两遍法的输出没留；M0 的 `bf16/*_dur.wav` 就是两遍法）；
- `sp_accel2/*_1p.wav`、`sp_accel_s12/*_1p.wav`：flash-attn 加速 25 步 / 12 步。
- 英文原声在 `_orig_v2/`。每轮 GPT 采样不同，同一句不同目录不是同一个「take」，只能比整体听感。
  要听的：Omni 版（不做束搜索、DiT 用 bf16）和 M0 听审包比有没有变差。

## 遗留问题和建议

1. **裁静音后偏短约 6%**：倍率控制的是含首尾静音的长度，而目标是开口到收口。静音长度每句不同（0–0.8 秒），GPT 之后看不出来。
   可行的改法：S2M 出 mel 后先按能量找首尾静音、按实际语音长度重算倍率，只重跑 S2M（Omni 版 S2M 约 0.3 秒）；
   或者放任，播出器按 `audio_s` 对齐开口、结尾早收 6% 对同传式配音影响不大。
2. **倍率触界多**（49 句里 16–20 句）：中文比英文原句短，>1.25 时只能按 1.25 念、提前收口。放宽翻译字数上限（M0 已建议 5.5 字/秒）能直接减少。
3. **Omni 的音质要人听一遍**（见上）；若不满意，退到 `--backend local --accel --compile`（RTF 0.50）或 eager。
4. **倍率回传靠文件**，只在串行下成立；将来要并发得改成响应头（补丁里再加一处）。
5. **每次请求都把参考音频 base64 发过去**（音色和情绪各一份），实测不影响（短句 0.6 秒已含）；
   Omni 有「上传音色」接口，说话人固定后可以换成按名字引用。
6. **504 路径没实测**（Omni 下最慢一句约 2 秒，碰不到 20 秒）。
7. 进程内后备还能再快：Omni 的 S2M 快，主要因为 DiT 用 bf16 + compile；`DubEngine` 的 S2M 现在是 fp32（上游写死关掉了 autocast），
   包一层 bf16 autocast 估计能省一半 S2M 时间，没测。
8. Omni 的 vLLM 是 0.30.0（CUDA 13.2 的 torch 2.13），和 WSL 里别的 vLLM 环境相互独立；升级 vLLM-Omni 时补丁要重打（`git apply` 失败就是上游改了那几处）。
