## 1. 结论先行

| 角色 | 选择 | 一句话理由 |
|---|---|---|
| **主力（本机 GPU）** | **腾讯 Hy-MT2-7B，GGUF Q4_K_M（4.62 GB）**，用 llama.cpp 的 `llama-server` 跑；翻译显存预算够约 7.5 GB 时换 Q6_K（6.16 GB） | Apache-2.0；翻译专用模型，没有思考模式；官方提供术语、上下文、风格、个性化模板 [1][2][3]。厂商自报的英语方向成绩与 DeepSeek-V4-Pro、GPT-5.5 的非思考模式同档 [4]；它的 7B 前身在 WMT25 英→中人评排第 2–4 名 [5] |
| 显存 ≤5 GB 时 | Hy-MT2-1.8B（FP8 2.04 GB，走 vLLM；或 GGUF Q8_0 1.91 GB，走 llama.cpp）；或者 7B 的部分层放到 CPU | 质量明显低于 7B，但还高于同尺寸的通用模型 [4] |
| CPU 热备 | Hy-MT2-1.8B GGUF（Q4_K_M 1.13 GB / Q8_0 1.91 GB），llama.cpp 跑 12 线程 | GPU 被挤满或 OOM 时顶上；单句约 2–5 s（推测），在 D 的余量里可以接受 |
| API 备选 | DeepSeek-V4.1-Flash（关思考）→ Qwen-MT-flash | 本地质量不够或放不下时启用；每小时 ¥1–2 以内 [6][7] |
| 不选 | Hy-MT2-7B FP8（8.05 GB，超预算）；Hy-MT2-30B-A3B（新架构，只有 FP8）；通用小模型或 MoE（Gemma 4、Qwen3.6-35B-A3B）；TranslateGemma、Seed-X（模板固定）；Sakura、Tower+（禁止商用） | 理由见 2.1 和 3.2 |

**四个重点问题的简答**
1. **放得下什么**：7B 的 Q4_K_M 整模型放 GPU，总占用约 5.5–6 GB（推测），单句约 1 s。1.8B 约 2.5–3 GB，单句约 0.5 s。FP8 只有 1.8B 放得下。引擎首选 llama.cpp（Windows 原生或 WSL 都行）；vLLM 0.26 只适合跑 1.8B 的 FP8 或 HY-MT1.5-7B 的 GPTQ-Int4。明细见 2.1、3.2。
2. **放 CPU / 内存**：1.8B 在 CPU 上可以当热备。7B 纯 CPU 跑太慢，只能当最后兜底；7B 把 20–30% 的层放 CPU 还可用，约 20–35 tok/s（推测）。「MoE 专家放 128 GB 内存」这条路：Hy-MT2-30B-A3B 的新架构在 llama.cpp 里是否支持未核实；通用 MoE 的翻译分又低于 Hy-MT2-7B [4]，不划算。见 3.3。
3. **小模型怎么补质量**：
   - 用官方的「个性化」模板，带前 2–4 句、后 1 句；
   - 只注入本句命中的术语；
   - 按 n-gram 重叠挑 2–3 条相似例句；
   - 输出纯文本，JSON 和各种标志由外部代码处理；
   - 术语和字数做后校验，不合格重试；
   - 量化不要低于 Q4，显存允许就用 Q6；
   - ASR 热词和术语表同源。
   见 1.3、3.4。
4. **关掉思考**：Hy-MT2 系列本身没有思考模式。通用模型的关法：
   - Qwen3.5：`enable_thinking:false`；
   - Qwen3-2507 Instruct：只有非思考模式；
   - Gemma 4：system 开头不放 `<|think|>`；
   - llama.cpp：`--reasoning-budget 0` 或 `--chat-template-kwargs`；
   - vLLM：请求里带 `chat_template_kwargs`。
   见 3.5。

### 1.2 本地调用与提示词草案（Hy-MT2-7B）

**服务**（参数名来自 llama.cpp 服务端文档 [15]；采样值为 Hy-MT2 官方推荐 [2]）
```
llama-server -m Hy-MT2-7B-Q4_K_M.gguf -ngl all -c 4096 -np 1 \
  --flash-attn on --cache-type-k q8_0 --cache-type-v q8_0 \
  --temp 0.7 --top-p 0.6 --top-k 20 --repeat-penalty 1.05 --port 8081
```
- temperature 另外与 0.3 做 A/B，看字幕的稳定性。

**提示词**：套用官方「个性化翻译」模板。官方格式是「【待翻译文本】…【翻译任务】1、…2、…N、将【待翻译文本】翻译为{目标语言}」[3]。示例：
```
【待翻译文本】
{当前句原文}

【翻译任务】
1、这是英文直播（{频道/发布会名}）的语音识别结果，可能有识别错误或半截句，按上下文最可能的意思翻译。
2、上文，仅供理解，不要翻译：{前 2–4 句原文}
3、下文，仅供理解，不要翻译：{后 1 句原文或 ASR 中间结果}
4、参考下面的翻译：{Apple Intelligence} 翻译成 {Apple 智能}；{iPhone 17 Pro} 保留为 {iPhone 17 Pro}
5、译文用简洁口语的中文直播字幕风格，不超过 {N} 个字，句末不加句号。
6、将【待翻译文本】翻译为简体中文。
```
- 要和官方「术语模板加上下文」的写法做 A/B。
- Hy-MT2-7B 在多约束指令上的得分明显低于单约束：IFMTBench 72.67 对 89.73 [4]。所以约束条数要尽量少，每一条都要后校验。

**调度与后处理**
- 当前句 ASR 定稿后发请求。下文用下一句的 ASR 中间结果，最多等 4 s。
- 字数预算 N = ⌊时长（秒）× 4.5⌋，最少 4 字。
- 输出只要纯文本：
  - 「跳过」由外部规则判断：只有语气词、ASR 置信度过低；
  - 「合并」由切句器决定，不让模型输出标志。原因是它的通用指令遵循较弱：IFEval 86.14，Multi-IF 更低 [4]。
- 校验与重试链：
  1. 超出字数 10%：再请求一次，把上限压到 N−2；
  2. 仍超：交 TTS 变速（建议不超过 1.15×）；
  3. 再超：在上限以内的最后一个分句处截断。
- 本地 3 s 没回、OOM，或者术语校验连续两次失败，就转 API 备选（DeepSeek；它失败再转 Qwen-MT）。

### 1.3 发布会术语表的做法

**1. 条目结构**（示例，中文译名以官网中文站为准）
```yaml
event: "Apple 秋季发布会 2026"
defaults: {unknown_proper_noun: keep}      # 没收录的专有名词默认保留英文
terms:
  - src: "Apple Intelligence"
    variants: ["apple intelligence", "Apple Intel"]   # ASR 常见写法
    zh: "Apple 智能"
    policy: translate                                  # translate | keep | keep_first_annotate
  - src: "iPhone 17 Pro"
    variants: ["iPhone seventeen Pro", "I phone 17 pro"]
    zh: "iPhone 17 Pro"
    policy: keep
    tts: "iPhone 十七 Pro"                             # 给配音用的读法
  - src: "nits"
    zh: "尼特"
    policy: translate
```
- **层级**：全局（通用科技词）→ 厂商（公司、高管、历代产品）→ 本场（新品、新功能）→ 会话（本场首次出现时记下的译法）。越具体的层级优先。
- **默认策略**：
  - 产品名、型号保留英文；
  - 有官方中文名的功能、技术用官方名；
  - 价格写成「999 美元」；
  - 单位按中文科技媒体的惯例。

**2. 会前（T−1 天）**
- 从这些地方整理词条：官方新闻稿、官网中文站、往届发布会的官方中文字幕和中文媒体报道、规格页。
- 按爆料清单预置可能出现的新品名。
- **同一份表导出成 ASR 热词**，从源头减少专有名词识别错误（需要和 ASR 那边对齐）。

**3. 会中**
- **匹配**：先把文本规范化（小写、去掉空格和连字符、统一数字读法），用 Aho-Corasick 加变体表，在「当前句 + 上下文」里找命中词。
- **注入**：只注入命中的条目，每句不超过 10 条。
  - 依据一：Qwen-MT 官方也建议只传与当前句相关的条目 [7]；
  - 依据二：在提示里给出词典提示，可以改善罕见词和领域外词的翻译 [16]。
- **校验**：每个命中条目都要在译文里找到目标串。找不到就用术语模板重试一次；还不行就用占位符法：原文术语先换成 ⟦1⟧ 再翻译，译完还原（推测较稳，要实测对语序的影响）。
- **热更新**：运营在后台增删条目，只对之后的句子生效，已经播出的字幕不改。
- **自动发现**：连续出现的、没收录的大写词组，按默认策略保留英文，并提示运营确认；确认后写入「会话」层，后面强制一致。

**4. 会后**
- 人工修正回流到厂商层术语表和例句库，供下一场的 few-shot 使用。

## 3. 各候选要点

**3.1 Hy-MT2（首选）**
- 2026-05-21 开源 1.8B、7B、30B-A3B 三个尺寸，支持 33 种语言（含中、英、日、韩）[1]，许可证 Apache-2.0 [2]。
- 官方模板 [3]：基础、术语、风格、个性化、分隔符、结构化。没有默认 system 提示，文档也没提思考模式 [3]；技术报告称它是「fast-thinking」的翻译模型 [4]。
- 官方推荐采样参数：temperature 0.7、top_p 0.6、top_k 20、repetition_penalty 1.05 [2]。
- 7B 和 1.8B 的架构是 `HunYuanDenseV1ForCausalLM` [32][33]，vLLM 把它列为已支持 [34]；但 README 仍写着「从源码编译 vLLM」[1]，vLLM 0.26 能不能直接加载要实测。
- GGUF 的 Q4_K_M、Q6_K、Q8_0 用当前的 llama.cpp 就能跑；1.25-bit 和 2-bit 版本要等 PR #22836 [17]。
- 30B-A3B 是新架构 `HYV3ForCausalLM` [35]，只有 FP8 版本（约 30 GB，推测）。

**3.2 引擎选择**
- **llama.cpp（首选）**
  - Windows 原生和 WSL 都能跑，官方就有 GGUF [17]。
  - 显存用多少就占多少，便于和 ASR、TTS 共存（经验）。
  - 默认开启提示缓存；KV 可以量化成 q8_0；可以设并发槽；提供 OpenAI 兼容接口 [15]。
  - 用 Windows 构建包时要确认包含 sm_120（需 CUDA 12.8 以上），未核实。
- **vLLM 0.26**
  - 不支持 Windows 原生，只能在 WSL 里跑 [36]。
  - 这张卡上 FP8 和 INT4 可用、INT8 W8A8 不可用（本机笔记）。
  - 启动时会按比例预占显存（经验），适合单独跑 1.8B-FP8 或 HY-MT1.5-7B 的 GPTQ-Int4。
  - 模型要先拷进 WSL 自己的盘，走 9P 读 Windows 盘的随机读极慢（本机笔记）。
- **SGLang**：只支持 Linux，Hy-MT2 需要从源码构建 [1]，暂不推荐。
- **速度的推算依据**：llama.cpp 公开跑分里，RTX 5060 Ti 16GB 跑 Llama-2-7B Q4_0：生成 93.5 tok/s，prompt 处理 4,196 tok/s（开 flash attention）[37]。按模型体积换算：
  - 7B Q4_K_M：约 75 tok/s；1,000 token 的提示加 60 token 输出，约 1 s；
  - Q6_K：约 1.3 s；
  - 1.8B：约 0.5 s。
  - 以上都是推测；与 TTS 同时跑 GPU 时会更慢，必须实测。

**3.3 CPU / 内存方案**（Ryzen 9 7900，12 核，双通道 DDR5，128 GB）
- CPU 生成速度大约等于「内存带宽 ÷ 模型体积」。4 条内存通常跑不到标称频率，按实际带宽 40–60 GB/s 估（推测）：
  - 1.8B Q8_0：约 20–30 tok/s；Q4_K_M：约 35–50 tok/s；
  - 7B Q4_K_M：约 8–12 tok/s。
- CPU 处理 prompt 很慢：7B 约几十到一两百 tok/s（推测），1,000 token 的提示要 5–20 s。所以 CPU 方案必须：
  - 依赖提示缓存（llama.cpp 默认开 [15]）；
  - 固定部分放在提示前面（术语模板那种写法），把变化的部分压到 300–500 token。
- 结论：
  - **1.8B 在 CPU 上当热备可行**，约 2–5 s/句（推测）。
  - 7B 纯 CPU 约 8–15 s/句，只能当最后兜底。
  - 7B 部分层放 CPU（`-ngl` 取 20–26）约 20–35 tok/s，是 4–5 GB 预算时的折中。
- 「MoE 专家放内存」：llama.cpp 有 `--cpu-moe` / `--n-cpu-moe` [15]，但：
  - Hy-MT2-30B-A3B 的新架构在 llama.cpp 里是否支持未核实；
  - 通用 MoE（Qwen3.6-35B-A3B、Gemma4-26B-A4B）的翻译分低于 Hy-MT2-7B [4]。
  - 所以不走这条路。
- vLLM 在 WSL 里没有 UVA（本机笔记），它的 CPU offload 大概率用不了（推测）。

**3.4 小模型补质量**（按收益排序，推测，需实测验证）
1. **术语**：只注入命中的条目，外加后校验（见 1.3）。词典提示对罕见词和领域外词有效 [16]。
2. **上下文**：带前 2–4 句、后 1 句。有研究表明，带上下文的提示能改善 LLM 的篇章级翻译 [38]。小模型的上下文窗口是 8K [1]，窗口不宜过长，要测 0/2/4 句三档。
3. **少样本**：从频道例句库里按 n-gram 重叠挑 2–3 条。相似例句能稳定提升质量，而 1 条不相关的噪声例句可能造成灾难性下降 [39]。
4. **少约束、纯文本输出**：多约束、JSON、标志交给外部代码处理（依据见 1.2）。
5. **量化**：Q4 主要伤的是指令遵循 [4]，显存允许就上 Q6_K。
6. **ASR 热词与术语同源**：从源头减少专有名词的识别错误。
7. **以后再做**：租云 GPU 用直播和发布会语料做 LoRA 微调，Hy-MT2 附了训练指南 [1]；要注意训练数据的版权。

**3.5 关掉思考**
- 天生没有思考模式：Hy-MT2、HY-MT1.5（翻译专用）、TranslateGemma、Seed-X。
- Qwen3.5：默认开思考，用 `chat_template_kwargs={"enable_thinking":false}` 关 [40]。
- Qwen3-*-Instruct-2507：只有非思考模式，不会输出 `<think>` [41]。
- Gemma 4：只有 system 开头放 `<|think|>` 时才思考，不放就不思考 [21]。
- 引擎层面：
  - llama.cpp：`--reasoning-budget 0`，或 `--chat-template-kwargs '{"enable_thinking":false}'` [15]；
  - vLLM：在请求里带 `chat_template_kwargs`。
- 兜底：输出里只要出现 `<think>`，就判为这次请求失败。

**3.6 日→中、韩→中（从简）**
- Hy-MT2 支持日语和韩语 [1]。
- WMT25 日→中人评里，混元参赛系统在第一梯队（−6.1）[5]。
- 韩→中没有找到公开数据。等英语跑通后再测。

## 4. 落地风险与绕法

1. **显存峰值**：TTS 克隆音色时可能冲高，同卡 OOM 会连带翻译挂掉。
   - 翻译服务用 llama.cpp，按需占用；
   - 看门狗发现 OOM 或超时，就切到 CPU 上的 1.8B 或 API；
   - 验收以 `nvidia-smi` 的峰值为准。
2. **GPU 争用导致延迟抖动**：翻译请求很短，但会和 TTS 抢算力。要在 ASR、TTS 同时满载时测 p95（见实测清单第 6 项）。
3. **Q4 指令遵循下降**：术语后校验必须做，显存够就用 Q6_K。
4. **评测偏差**：厂商自报的自动指标偏向混元系统 [5]，选型以我们自己的人评为准。
5. **发布会的新名词**：会中临场出现，靠运营热更新加自动发现来兜；已经播出的译文不改。
6. **API 备选**：
   - 国内 API 的审核可能拦截：百炼返回 400 [27]；DeepSeek 没有公开说明；
   - 海外 API 的支持地区不含中国大陆 [29]；
   - 所以 API 只在本地不够用时启用。
7. **许可**：Hy-MT2 是 Apache-2.0，可以商用；Sakura（CC BY-NC-SA）和 Tower+（CC-BY-NC）禁止商用，要避开 [42]。

## 5. 建议的实测清单

以下通过线都是建议值。

| # | 测什么 | 样本 | 指标 | 通过线 |
|---|---|---|---|---|
| 1 | 英→中质量 | 用我们自己的 ASR 输出，共 3 h：游戏、杂谈、VTuber、**发布会**各约 45 min；抽 300 句请双语者标注 | ESA 人评分、major 错误率；LLM 评审做全量排序。参测：7B Q4 与 Q6、1.8B、HY-MT1.5-GPTQ、DeepSeek | 7B 人评不低于 DeepSeek 减 3；有 major 错误的句子不超过 5% |
| 2 | 提示词消融 | 样本 1 | 基础模板对个性化模板；前文 0/2/4 句；后文 0/1 句；少样本 0/2 条 | 选最优组合 |
| 3 | 发布会术语 | 3 场往届英文发布会，配官方中文命名，整理 200 条术语，含 ASR 变体 | 命中率、一致率、占位符法对语序的影响 | 不低于 95% |
| 4 | 字数 | 全量样本 | 首轮达标率、压缩重试一次后的达标率 | 85% / 98% |
| 5 | 思考泄漏 | 全量样本 | 输出里出现 `<think>` 的比例 | 0 |
| 6 | 显存与速度 | 与 ASR、TTS 同时满载跑 4 h | 翻译进程的显存峰值、tok/s、p95、有无 OOM | 预算以内；p95 ≤ 2 s；不出现 OOM |
| 7 | CPU 热备 | 用 `llama-bench -t 12` 分别测 1.8B 和 7B，再做端到端测试 | prompt 处理和生成速度、单句 p95 | 1.8B p95 ≤ 5 s |
| 8 | API 备选 | 1 h 真实节奏 | p95、错误率、审核拦截率、费用 | p95 ≤ 2.5 s；失败率 ≤ 1% |
